# Self-audit, November 2026

What a backend engineer reviewing this repository for a hiring decision would notice in the first
ten minutes, and what to improve next. Written 2026-11-15 against `main` at `6528af0`, with the
fixes that followed listed at the end.

## First ten minutes

### README, first screen (before)

- Strong: one-line pitch, feature list, "Architecture in one minute", a stack table, a working
  `make up`. Data licensing is handled explicitly.
- Weak: no picture of the product, no status badges, and the live link said "deployment in
  progress" although the site has been up for weeks. The parts that make this project stand out
  for a backend role (outbox, exactly-once e-mail, module contracts, query-count tests) were only
  findable by reading `docs/`. A reviewer skimming for 30 seconds sees "a Django + Next.js F1 site".

### Architecture clarity

- Very good. `docs/architecture.md` has a container diagram and an event sequence diagram, six
  ADRs explain the non-obvious choices (Next.js, session auth, transactional outbox, data sources,
  self-hosting, Google sign-in), and `import-linter` enforces "modules never import each other's
  models" in CI with one contract per module, which is the claim a reviewer would try to break first.
- `docs/events.md` was out of date: the two central scheduler events (`SessionResultsDue`,
  `AnalyticsDue`) were missing, `PracticeResultsDue` had the wrong key, and the
  `RaceResultEmailRetry` row sat below the table with a payload field (`user_ids`) the code does
  not send.
- `docs/PLAN.md` is in Polish and reads like private notes (mentions the CV, a DigitalOcean
  deployment that never happened, "repo prywatne" for a public repo). It is the third link in the
  README. Recommendation: translate the decisions table and status into English, or move the file
  out of the main docs path.
- `docs/operations.md` refers to "written approval from Company Management" for new copyleft
  dependencies, which does not fit a personal project and will raise an eyebrow.

### Tests and coverage

- 932 backend tests on real PostgreSQL (factory_boy, recorded API fixtures, no network), 90%
  coverage gate (actual about 96%), about 30 query-count assertions on API endpoints, idempotency
  and double-delivery tests for the outbox, Vitest on the frontend and Playwright end-to-end tests
  against the full Docker Compose stack in GitHub Actions. This is well above what reviewers
  usually see in a junior portfolio.
- Gap: nothing guarded repeated queries outside the API endpoints that have explicit counts
  (background jobs, demo reset, imports). Addressed with pytest-queryguard, see
  [n-plus-one.md](n-plus-one.md).
- Backend tests need PostgreSQL, so contributors on small machines depend on CI or `make db`.
  That is a deliberate choice (ADR and testing.md) and is fine.

### CI health

- `CI` and `E2E` were green on every push.
- `Audit` (weekly osv-scanner and npm audit) had been **red for three weeks**: undici 8.12.1 (dev,
  via jsdom) gained eight advisories, a new minimatch advisory had no fix in the range
  typescript-eslint accepts, and a stale ignore was still listed. A red badge on the front page is
  the first thing a reviewer sees. Fixed in PR #1.
- All workflows use actions pinned to `@v4`/`@v5` majors that run on the deprecated Node 20
  runtime (warnings on every run). Not urgent, cheap to bump.
- The CI workflow has no `concurrency` group (E2E has one), so superseded pushes keep running.

### Code quality

- Consistent module layout (`models`, `services`, `selectors`, `selectors_public`, `handlers`,
  `api`), small public interfaces between modules, docstrings that explain *why*, commit messages
  that describe behaviour. Ruff (format and lint) is enforced.
- Ruff selects only `E, F, I, UP, B, DJ`. Adding `SIM`, `RET`, `PT` and `S` (bandit) would be a
  visible signal; expect a few dozen small fixes.
- Pyright runs in CI as a ratchet: the error count may only go down. The baseline was 130 errors,
  almost all from Django patterns pyright does not understand without a plugin (`<fk>_id`
  attributes, reverse relations, `get_user_model()` returning the abstract base). They are fixable
  with explicit annotations on the models and the concrete `User` import inside `accounts`
  (done in PR #4: 14 left, all queryset annotations and third-party base types).

### Security basics

- Session auth with CSRF on one origin (ADR 002), secure cookies and HSTS when `DEBUG` is off, a
  Content-Security-Policy on the frontend, throttling for anonymous API callers and login, a shared
  secret on the internal revalidation route, a redaction filter on logs, custom `check --deploy`
  rules (development secret key, missing hosts), weekly dependency audits.
- `SECRET_KEY` silently falls back to a development value when the variable is missing; only
  `check --deploy` catches it. Failing at start-up when `DEBUG` is off would be stricter, but it
  needs the test settings to set a key first. Low risk, noted.

### Performance

- API endpoints were already protected by query-count tests, and pytest-queryguard confirmed it:
  no lazy relationship loads anywhere in the application code.
- It did find repeated statements in background code. The worst was the nightly demo reset, which
  ran the same race-outcome query once per bot pick; a test running one reset went from 130 SQL
  statements to 60 (details in [n-plus-one.md](n-plus-one.md)).
- A dependency-free load-test script exists (`scripts/perf/load_test.py`); its results are not
  published anywhere. A short table in the README or docs would back the performance claims.
